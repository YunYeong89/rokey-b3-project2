## 4. Validator 구현 범위

구현됨(AABB 근사): 1. 주문 상품/수량 누락, 1. 주문에 없는 item_id, 2. 상품 중복 배치, 3. 포장 공간 경계 위반, 4. 상품 간 충돌, 5. 허용 배치 방향 위반, 6. 상부 적재 금지 상품 위 적재, 7. 허용 적재 하중 초과, 8. 지지면 부족(공중 부양 포함), 9. 무게중심 투영점이 지지 볼록껍질 밖, 10. 최대 적재 층수 초과, 11. 담기 순서 위반(지지 상품보다 먼저 배치 / 순번 오류)

미구현/근사 한계:
- 실제 무게중심(내용물 분포) — 외접 직육면체의 기하 중심으로 대체
- 원통/원뿔대 형상의 정확한 충돌 — AABB로 보수적으로 근사(실제로는 닿지 않는 캔끼리도 충돌로 판정될 수 있음)
- 신라면 컵 원뿔대 형상의 윗면/아랫면 크기 차이
- 마찰, 상품 변형, 봉투 변형/들림, 동역학(운반 중 흔들림)
- 그리퍼(RG2) 접근 경로 및 손가락 간섭(swept volume), 봉투 입구(300×240mm) 통과 경로
- 로봇 도달 가능성/작업 시간

### 6.2 실패 원인

**Experiment 1·2: 치수 지식 부족이 주된 원인**
- 모든 상품을 1층(바닥)에 두었다. z는 LLM이 스스로 가정한 높이의 절반으로 잡았는데, 가정한 높이가 DB와 달라서 7개 상품 전부가 바닥에 닿지 않거나(공중 부양) 바닥 아래로 파고들었다.
  - 참치캔: 높이를 90mm로 가정(DB 40mm) → 바닥에서 25mm 떠 있음
  - 신라면 컵: 높이를 70mm로 가정(DB 110mm) → 바닥 아래 20mm
  - 코카콜라: 높이를 120mm로 가정(DB 122mm) → 1mm 파고듦. 허용 오차가 0.5mm이므로 위반으로 집계된다.
- Text-only는 Run 2에서 코카콜라를 "500ml 페트병"으로 가정했다(실제는 355mL 캔). 상품명만으로는 규격(variant)을 알 수 없다는 점이 그대로 드러났다.
- Vision을 추가해도 개선은 일부에 그쳤다. 코카콜라 치수(65×65×125)는 거의 맞혔지만, 스팸은 80×50×120으로 가정해 세로로 길게 놓인 것처럼 처리했고, 쫄병스낵에는 빼빼로와 같은 치수(40×190×45)를 적었다. 사진이 선반 전체를 멀리서 찍은 것이고 크기 기준 물체도 없어서 절대 치수를 추정하기 어려웠을 것이다. 사진 입력 때문에 Input tokens가 약 840개 늘었다.
- x·y 배치도 90~100mm 간격의 격자에 중심을 두는 방식이어서, 실제 폭과 10mm 벽 여유가 반영되지 않았다.

**Experiment 3: 치수는 정확하지만 좌표 계산에서 오류**
- 주어진 치수와 무게를 그대로 사용했다. 바닥에 놓인 상품은 z가 모두 정확했다(Run 2에서 바닥 상품 5개 모두 1층으로 확인됨).
- 남은 위반은 산술 및 기하 처리 오류였다.
  1. 폭이 다른 상품들을 같은 x 중심(43, 155, 267)에 배치해 벽 여유를 위반했다. 신라면은 x −7~93, 스팸은 217~317.
  2. `flat` 자세로 바뀐 외형을 반영하지 않았다. 빼빼로를 flat으로 두면 y 방향 길이가 155mm가 되어 벽 밖으로 나간다.
  3. 2층 z 계산이 틀렸다. 쫄병스낵의 z를 77.5로 잡았는데, 참치캔 윗면 40mm + 쫄병스낵 높이 55/2 = 67.5여야 한다. 빼빼로의 z(110)도 틀려서 두 상품 모두 공중 부양으로 판정됐다.
- Run 2에서 Experiment 3만 유일하게 2층 적재를 시도했다(스팸 위 빼빼로, 참치캔 위 쫄병스낵). DB상 적재 허용 여부와 하중(48g, 87g < 300g)은 지켰다. 하지만 z를 고쳐도 쫄병스낵의 지지 면적은 참치캔 내접 정사각형 60×60 = 3,600mm²로, 쫄병스낵 바닥 면적의 약 21%에 불과하다. 30% 기준에 못 미치므로 다시 실패한다.
- Run 1에서는 같은 입력이었는데도 빼빼로를 바닥에 놓은 상태로 z = 77.5(upright 높이 기준)를 적어 공중 부양이 됐다. temperature=0으로 설정해도 같은 입력에 대한 출력이 달랐다.

**보조 지표 (LLM이 스스로 가정한 치수로 검증)**: 세 조건 모두 자기 치수 기준으로도 4~11건의 위반이 났다. 즉 gpt-4o는 물리 정보가 정확해도 좌표 산술(벽 여유, 상품 간 간격, 자세에 따른 축 교환, 적층 높이)을 안정적으로 수행하지 못한다. 다만 LLM이 flat 상품의 치수를 이미 눕힌 상태로 적은 경우가 있어서, 이 보조 지표에도 잡음이 섞여 있다.

### 6.3 결론: 물리적 특성 DB가 도움이 되는가

- **도움이 된다.** 위반이 16~18건에서 4~7건으로 줄었고, 치수·무게 오추정과 그에 따른 바닥 접촉 실패가 사라졌다. 적재 허용 상품을 근거로 2층 적재도 시도했다. Vision은 Text-only 대비 개선 폭이 작았고, 토큰만 가장 많이 썼다.
- **DB만으로는 충분하지 않다.** DB를 받은 경우에도 유효한 계획은 0건이었다. 남은 오류는 정보가 부족해서가 아니라 LLM의 좌표 계산 능력 때문이다. 따라서 "LLM이 mm 좌표까지 직접 생성"하는 구조는 로봇 실행 계획으로 쓰기에 적합하지 않다.
- 다음 단계로는 역할을 나누는 구조를 권장한다. LLM은 담기 순서, 그룹, 적층 관계(무엇을 무엇 위에 둘지) 같은 정성적 결정만 하고, 결정론적 배치기(Python)가 DB 치수로 좌표를 계산한다. 그 결과를 Validator로 검증하고, 실패 시 재계획한다.

### 6.4 한계

- 조건당 2회(Run 1·2)이고 모델은 gpt-4o 하나뿐이다. 이 API Key로는 `gpt-4o`, `whisper-1`만 조회되며, README 기본값인 `gpt-5.5`는 404였다.
- 상품 DB 값은 개발용 근사값이다. 정답 치수 자체가 실측값이 아니다.
- Validator는 AABB 근사이며 접촉 허용 오차 0.5mm는 엄격한 편이다. 오류 하나가 여러 항목에 중복 집계될 수 있다(예: z<0이면 경계 위반과 지지 부족에 동시에 집계).
- 사진은 주문 상품 7개만이 아니라 보유 상품 12개 전체를 선반 위에서 찍은 것이며 크기 기준 물체가 없다.
- 자세 정의(flat = depth↔height 교환)가 LLM에게 직관적이지 않았을 수 있다.
- 비용은 공개 단가로 계산한 추정치이며 실제 청구액이 아니다(Run 1 약 $0.037, Run 2 약 $0.039).
